## 4. Detailed Evidence (key extracts)

### Auth (T02–T07)
- Login response shape: `{success:true, data:{user:{id, email, full_name, role, employee_id}, employee}}` — matches API contract.
- Cookie: `#HttpOnly_localhost ... sid s%3A...` — httpOnly confirmed.
- T03/T04 responses byte-identical except request_id/timestamp: `{"code":"INVALID_CREDENTIALS","message":"Invalid email or password"}` — no user enumeration.
- T07: logout → `{"success":true,"data":null}`; subsequent /auth/me → 401 SESSION_INVALID (server-side destruction confirmed).

### RBAC (T08, T13a, T15, T17)
- Enforced correctly on every implemented route tested: ADMIN-only users module; HR_MANAGER+ employee writes; payroll-role reads on salary config (verified pre-restart in earlier session and via 401-gating after).

The valid-case test was rerun against the contract-free smoke employee (T16c: 201) and status transition worked (T16d: 200 → DRAFT).

## 5. Environment Incident (full disclosure)

During T17 the running API (uptime ~2h, started ~20:14 IST behind a WSL relay) was found to be serving **stale code** — `GET /api/v1/salary-structures` returned 404 despite the module existing in source. A restart was attempted per the smoke plan:

1. The process listening on port 4000 (a `wslrelay` — WSL port-forward relay) was terminated. **This killed the relay to the user's original API process; the original API is no longer reachable and could not be restored.**
2. A fresh API was started from current source on Windows (`npm run start`) — health 200.
3. The fresh API **cannot reach the database**: `backend/.env` credentials (`pay365/pay365@localhost:5433`) are **rejected by the only running PostgreSQL** (Windows service `postgresql-x64-18`, custom install at `D:\PROJECTS\Postgre\data`, PG18) — verified directly with psql over IPv4 and IPv6 (`FATAL: password authentication failed for user "pay365"`).
4. Docker Desktop is not running (compose db unavailable); WSL Ubuntu has **no node, no postgres, and no listeners** on 5433/4000 (verified via `ps aux` and `/proc/net/tcp`).
5. Conclusion: the original working stack used a database endpoint/credentials **not recorded in the repo's `backend/.env`** (likely a WSL-side postgres that is now stopped, or shell-exported credentials). **The user must provide the correct DB credentials or start procedure** to unblock T17–T20.
6. Current state left behind: API running on current code (health OK, DB-backed endpoints non-functional); PostgreSQL service untouched and running.
